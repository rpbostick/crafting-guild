# Changelog

Versions of Crafting Guild. `ws version` prints the current one.

## 2.6.1

- `ws alerts [on|off|status|test]` adds two comfort features for the person running sessions, with no model and no tokens spent. A break reminder every `break_minutes` (30 by default) shows a `notify-send` pop-up, and an attention indicator fires when the orchestrator needs an answer: after `alert_after_seconds` (20) of waiting it raises a pop-up, writes `WAITING · <project>` to the session's terminal title and appends a tab-separated line to `~/.local/state/crafting-guild/attention.log`; `repeat_minutes` re-alerts until the wait ends, which clears the title. Both agents call one handler, `scripts/attention.sh`: Claude Code through a `Notification` hook whose matcher names the `permission_prompt` and `idle_prompt` types plus `UserPromptSubmit`/`PreToolUse`/`PostToolUse` resume hooks, OpenCode through `scripts/opencode-plugins/attention.js`. `on` merges `docs/alerts-claude-hooks.json` into `~/.claude/settings.json` (backed up first), links the plugin into `.opencode/plugins/` and enables `ws-break.timer`; `off` removes exactly those; `status` shows each piece and the config in effect; `test` raises one sample pop-up and log line. The config is `~/.config/crafting-guild/alerts.conf` (every key in `docs/alerts.conf.sample`): `visual`, `sound`, `sound_file`, `volume`, `break_minutes`, `break_message`, `quiet_hours`, `alert_after_seconds`, `repeat_minutes` and `attention`. Quiet hours suppress the pop-up and the sound but still log; `attention=off` or `break_minutes=0` switches one piece off. The break check runs every minute and decides from `~/.local/state/crafting-guild/break.last` whether a break is due, so a config change needs no unit reload.
- The status line starts with the clock and the last `ws chain` event with its time (`20:15 · ws <project> · last: 20:11 <name>: merged (...)`), follows the session's pinned project (`WS_PROJECT`), and with `WS_STATUS_ALL=1` shows the newest event across every project.
- `ws merge` passes over modified tracked files under `plans/` or `reports/` that the branch being merged does not touch, leaving them modified and out of the merge commit, the test run and the push. Any other modified tracked file still refuses, as does a branch that touches one of those plans. Before, one orchestrator session's unsaved plan edit blocked every merge another session made into the workspace.
- `ws review-compare --fix-first [--limit N] [name...]` measures reviewer recall on the commits Claude marked fix-first: it pairs each chain-log `review at <sha>: fix-first` line with the automatic fix task for that round, reads Claude's blocking findings from the task's `## Blocking findings`, checks the SHA out in a scratch worktree and runs the OpenCode review against the same merge base. `ws review-compare --bench <slug> [--arm L] [--limit N] [run...]` does the same for bench runs whose verdict is fix-first, rebuilding each from its base and `replay.patch` with the run's evidence restored. Both write `runs/<project>/review-recall.tsv` (case, SHA, Claude blocking count, OpenCode verdict and blocking count, Claude findings named, verdict agreement), keep every OpenCode review under `runs/<project>/review-recall/`, skip a case whose SHA or fix task cannot be found with a note, and print verdict agreement and findings named per project and in total. Findings match on file and line within five lines, an approximate rule. The merged-SHA mode is unchanged.
- Every `ws review-compare` mode diffs a merged branch from its merge base (the merge commit's two parents' merge base) instead of the merge commit's first parent: when main gained commits after the branch started, the first parent made those main changes look like deletions the branch had made. A row a bench corpus recorded before this change keeps `merge^1` as its base, so its replay and recall review still start from main at merge time; re-adding the entry with `ws bench add` records the merge base. `ws bench add` records the same merge base as a replay's starting commit, so a bench replay and its recall review start where the original branch did.
- Shadow reviews: with `WS_REVIEW_SHADOW=opencode`, every deciding review (unless it already runs on OpenCode) also starts a detached OpenCode review of the same SHA and merge base in its own scratch worktree, written to `runs/<project>/shadow/<name>-<sha>.{json,md}` and paired with the deciding review in `runs/<project>/review-shadow.tsv` (verdicts, blocking counts, the Claude findings named within five lines, shadow-only blocking findings, cost). It never delays or changes the deciding review, a chain step or a merge, and a merge may remove the builder's worktree while it runs. `ws review-shadow [--project slug|--all]` prints verdict agreement, findings named (recall) and shadow-only blocking per project and in total. `WS_REVIEW_SHADOW_MODEL` (default `WS_OPENCODE_MODEL`) and `WS_REVIEW_SHADOW_BUDGET` set the shadow's model and budget, and `WS_REVIEW_MEM` caps it.
- Result check: a task header `UI: yes` marks a change the builder must render. Its run does not check out unless `.ws-evidence/` holds a `*.png`, `*.jpg`, `*.webp` or saved `*.html` snapshot, with the reason `UI task without a render in .ws-evidence/`. `agents/planner.md` marks a visible step with it, and `agents/builder.md` says the render shows the changed screen in the state the task changes, at phone width for a mobile or web app.
- Builder results carry `edge_cases` answers for platform, time, stored data and state that resets (`n/a` allowed with a reason): whether the change detects a browser, OS or runtime feature and the versions where it differs, whether output depends on the clock and the fake-timer test that crosses the boundary, whether a stored shape changed and the test that loads the old one, and whether user input survives navigation, backgrounding or reload. A full-track result missing an answer does not check out; a light-track one warns. `scripts/review.sh` puts the answers in the reviewer's prompt so a review can hold the builder to them.
- `ws teeth <name>` proves a branch's new tests can fail: it checks the branch tip out in a scratch worktree, puts every non-test file the branch changed back to its merge base (removing files it added), keeps the branch's test files (`TEST_GLOBS`, default covering the usual names) and runs `TEETH_CMD` (or `TEST_CMD`). It writes `runs/<project>/<name>.teeth.txt` and `runs/<project>/logs/<name>.teeth.log`: `ok` when the tests fail without the production change, `toothless` naming the test files that pass either way, `n/a` when there is no test or no production change, or `error` when the runner crashes before reporting a failure. `ws chain` runs it before every review and a `toothless` result is a blocking finding under rule 2 unless the reviewer says why the test is sound; `ws bench` records the verdict in a `teeth` column and reports the count per arm.
- `ws brief [--write] [--since <file>]` collects every registered project into one status page: what waits on you (a stopped chain, the exact merge command a gate names, a partial run with no process left), live builders, chains and previews, each plan's in-flight block, unmerged worktrees and `agent/*` branches, merges in the last 48 hours, and uncommitted `plans/` and `projects/` files, with idle projects on one line. `--write` saves reports/brief.md, keeps the previous as reports/brief.prev.md and ends with a line diff against it. `ws autostart on` installs `ws-brief.timer` (`OnCalendar=hourly`, `Persistent=true`), and cold start's `--brief` line names the file with its age and the waiting count.
- A project's `POST_MERGE_CMD` runs a chore after every successful merge, such as rendering review sheets, restarting a server or rebuilding a site. `ws merge` starts it detached in the main checkout under the preview memory cap, with `WS_MERGED_SHA`, `WS_MERGED_NAME` and `WS_PROJECT` set; it logs to `runs/<project>/post-merge-<name>.log`, records `ok` or `failed` in `runs/<project>/post-merge.status`, raises a desktop notification on failure, and never changes the merge's exit status. Cold start shows a failed one.
- `ws doctor` requires OpenCode `WS_MIN_OPENCODE` (1.19.1) whenever `WS_AGENT` or `WS_REVIEW_AGENT` is `opencode`, since the launchers use the server's `json_schema` output format and `experimental.*` plugin hooks: an older install fails then, warns otherwise, and a newer release on npm is reported as a note. OpenCode results and Claude dispatch records carry the CLI version they ran, so a capability change is traceable to an upgrade.
- `ws review --agent opencode` (or `WS_REVIEW_AGENT="opencode"`) runs the reviewer on OpenCode with a read-only permission config (reads, `git diff/log/show/status`, `cat` and `ls`; no edit, write, web or network tool), validates the review JSON against the same schema with one continue, and writes the same review files merge and chain read. `ws review-compare` runs that review beside the recorded Claude one for each branch, checking a merged branch out at its reviewed SHA, and prints the two verdicts, their blocking counts and the Claude findings OpenCode names within five lines.
- `WS_AGENT` set in the environment wins over `config.local.sh`, and the self-test runs with `WS_AGENT=claude`: a private config that made OpenCode the default builder failed the self-test's bench checks.
- `ws release` on the workspace itself no longer tries to build a release asset from its own `scripts/release.sh` (the release script, not a build), which failed the clean-clone step after the tag was pushed.
- `ws bench` keeps each replay's committed change as `runs/<project>/bench/evidence/<run>/replay.patch`, so a replay can be graded later, for example against the original builder's test files.
- `ws bench review <slug> [--arm L] [--limit N] [--dry-run] [runs...]` reviews the runs an earlier pass left unjudged (`--review none`, a skipped or interrupted review) from each run's saved `replay.patch`: it checks the base out in a throwaway worktree, applies the patch, commits, reviews blind under the run's opaque name, and writes the verdict and blocking count back into `runs.tsv`. It is resumable, and a patch that no longer applies is recorded `unreviewable` with the reason in the run's evidence directory instead of being skipped.
- `ws bench report` leaves `unreviewable` runs out of the merge-verdict rate and names them, so a replay whose patch no longer applies is not scored as a failed review.
- `ws tutor` opens a tutor tab: a Claude session in the course project named by `WS_TUTOR_PROJECT`, pinned to it, without a cold start.
- `ws autostart [on|off|status]` keeps services running across crashes and reboots as systemd user units started at login: the live app of each project in `WS_LIVE_PROJECTS` (`systemd/ws-live@.service`, running `scripts/live-app.sh`, restarted 20 s after a failure, under the preview memory cap), and with `WS_BENCH_AUTOSTART=1` the bench (`systemd/ws-bench.service`).
- A `ws merge --no-review` merge commit says "merged at <sha> with --no-review" instead of "reviewed at <sha>", so an override is visible in the history.

## 2.6.0

- Builders can run on OpenCode (`ws dispatch --agent opencode`, `WS_AGENT`, `WS_OPENCODE_MODEL`; default model `opencode-go/deepseek-v4.1-flash`). The task's grants become OpenCode's permission config (every other command and any write outside the worktree is denied), the run stops at its budget from the per-step costs OpenCode reports, the JSON result is checked against the same schema, and the result check, review, chain and merge work as for Claude Code. `ws tail` reads OpenCode logs too.
- `scripts/zdr-check.sh`: an OpenCode Go model is used only while OpenCode's page lists it as not used for training, kept 0 days, and under an unlapsed retention agreement; the launcher refuses it otherwise.
- The orchestrator can run under OpenCode: `AGENTS.md` (the brief, with OpenCode's mechanisms where Claude Code's differ), `opencode.json` (loads the private preferences and lessons when present; missing files are skipped), `/cold-start`, and `docs/opencode-orchestrator.md`. A self-test check keeps the `bin/ws` commands named in `CLAUDE.md` and `AGENTS.md` the same.
- `ws bench`: an arm can name its agent and model (`--arm L=<ref>,agent=opencode,model=<id>`), `--review none` grades on tests and done-when only, and `report --baseline recorded` compares with the tasks' first runs as recorded, without replaying them.

## 2.5.4 (not released separately: part of 2.6.0)

- `ws release` authors the public commit and tag as GitHub's no-reply address for the public repository's owner (or `RELEASE_NAME`/`RELEASE_EMAIL` from the conf), so the private repository's e-mail never reaches the public history.
- `ws release` publishes a GitHub Pages site when the conf sets `PAGES_BUILD` (and `PAGES_DIR`, default `dist`): it builds from a clean clone of the new tag, scans the output for home paths and keys, and pushes it to the public repository's `gh-pages` branch.
- `ws release`: the e-mail check skips third-party licence texts, manifests and lockfiles (as the attribution check already did), so a dependency author's address in `THIRD_PARTY_LICENSES` or `package-lock.json` no longer stops a first release.
- `ws merge` takes a per-project lock (`runs/<project>/merge.lock`), so two lanes that finish together merge one after the other instead of both working in the same main checkout. A second merge says it is waiting.
- `ws review`: when the reviewer model has reached its usage limit, the review runs once more on the light-track model (`WS_REVIEW_MODEL_LIGHT`) instead of failing, so a chain doesn't stop on it.
- `ws chain`: an automatic fix round's task keeps the original task's `## Commands` section, so the fix builder gets the same grants and can re-run its tests. Before, the section was demoted with the rest of the original task, the fix round got none of those grants, and it ended partial.
- Result check: a done-when item's evidence path is read without the punctuation after it (`.ws-evidence/a.log: 192 functions` names `.ws-evidence/a.log`), and a bare file name is also looked for in `.ws-evidence/`. Before, a trailing colon failed a run whose evidence was there, and some citations weren't checked at all.
- `ws chain` resumes a stopped run: a `NO RESULT` file (what a run stopped by hand or a closed session leaves) counts as no result, and a worktree with no run whose task has a line starting `Resume:` is dispatched again. Before, the chain stopped on the stale file as a failed check.
- Builders may run `git check-ignore` (read-only), and the builder lessons say to read files outside the worktree with the Read and Grep tools: the automation audit found Bash `grep`, `ls` and `git show --output` on outside paths among the most frequent denials.
- `ws chain` and the result check read a weekly limit's reset time ("resets Oct 19, 4am"), not only a clock time ("resets 8pm"), and never roll a dated reset to the next day. Before, a review that hit the weekly limit stopped the chain with "reset time unknown".
- `ws wait` checks a saved failing result again when the result check has changed since, so restarting `ws chain` after a fix to the check carries on instead of stopping on the old verdict.
- `ws merge` keeps the git-ignored files a builder made (a generated recording, a download) under `runs/<project>/evidence/<name>/ignored/` and names them, instead of discarding them with the worktree. Dependency, build and cache folders, `.ws-evidence` and linked paths are skipped; files over 20 MB are named, not kept.
- `ws dispatch` names the paths `.worktree-links` links into a worktree as read-only in the builder's prompt (writing through them is denied), and says where to save files that must outlive the run.
- `ws review` names any other project's plan that mentions the branch, so a branch kept waiting on purpose (for a demo or a recording) isn't merged by mistake.
- Builders may run `sha256sum` and `file` by default (both read-only), so checking a download no longer costs a denied call. `unzip` still has to be named in a task's `## Commands`.

## 2.5.3

- `ws dispatch`: a glob in a task's `## Commands` is not expanded against the workspace's files. `` `node *` `` is granted as `Bash(node*)`; before, it became `Bash(node agents*)` from the folder listing.
- `ws dispatch --dry-run` (and `--print-prompt`) leaves nothing behind: a worktree and branch it created for the dry run are removed, so a later dispatch branches from the main branch as it is then. A worktree that already existed (a resume) is kept.

## 2.5.2

- `ws dispatch`: a task command written `git -C <dir> <sub>` is granted as exactly that. Any other git command starting with an option is no longer granted; before, both became a grant for every git command (`Bash(git*)`).
- `ws audit`: a check script counts as in the suite when any script the test command runs names it, followed through more than one file (`run-all-tests.sh` calling `run-e2e.sh`), including by name without its extension. Wrapper calls from before `ws-run` existed, and hand runs of scripts the suite already runs, are no longer flagged.
- The selftest's shellcheck step fails the selftest on a warning. Before, it only skipped printing "shellcheck ok". The scripts are now shellcheck-clean (`.shellcheckrc` covers sourcing config files by a variable path), and `ws init`'s Node detection works in a repo with more than one `*/node_modules`.

## 2.5.1

- `ws release`: moving the `v<major>` branch no longer prints GitHub's pull-request hint, and the "version already exists" message names `VERSION` as well as `package.json`.

## 2.5.0

- **Versions and rollback.** Every `ws release` now creates a GitHub release page (notes from the published changelog, marked Latest), tags the private commit it published (`released-vX.Y.Z`), and with `RELEASE_MAJOR_BRANCHES=1` moves a public branch `v<major>` to the release, so users can install any exact version or the newest of a major version. `ws rollback <version>` puts the published files back to a release as one new commit, leaving everything outside `RELEASE_PATHS` alone; `--dry-run` lists what would change. README: Install a specific version.
- Release notes match the version exactly (2.3.1 no longer picks up 2.3.10's section).

## 2.4.0

- **Done-when, item by item.** Builders report every done-when item as met, partial or open, and whether they ran something to show it (`observed`, with the log or file) or reasoned it (`inferred`), plus what they could not establish (`unknowns`). The result check fails a `done` with an item not met and an observed item whose evidence is missing, and shows items met on inference alone. The reviewer gets the task's done-when and the builder's report, and treats an inference a user would hit as blocking.
- **`ws init --dry-run`** shows the conf it would write and the changes; an existing conf is replaced only with `--force`, after a backup, keeping keys init does not write.
- **`ws doctor`** checks the machine (bash, git, jq, GNU timeout, python3, the Claude Code version, systemd scopes, gh, rsync, shellcheck, the browser command), the workspace (the SessionStart hook, `ws` on PATH, lessons caps) and the selected project (path, branch, test command, remote, excludes), with a fix for each failure.

## 2.3.9

First public release.

- **One orchestrator session per project.** `ws <slug>` opens Claude Code in the workspace with the project attached; a SessionStart hook prints a cold start (git state, worktrees, running builders and chains, previews, the plan's in-flight block) at every start, resume and compaction. Sessions are pinned to their project; cold-start warns when another session moved the selection.
- **Headless builders in git worktrees.** `ws dispatch` runs `claude -p` on a task file in `<project>/.worktrees/<name>` on branch `agent/<name>`, with a dollar budget, a timeout that follows the task's track (45m light, 120m otherwise), a memory cap through systemd user scopes, and a grant of exactly the commands it needs (the task's `## Commands` section is granted; destructive forms never are). Gitignored environments and `file:../` siblings are linked into the worktree.
- **Checked results.** Every run returns a JSON result; `check-result.sh` verifies claimed commits and test logs against the branch, lists denied calls, and recognises a run stopped by the usage limit with its reset time.
- **Evidence outside the product.** Builders run checks through `ws-run`, which logs each command's real exit code under `.ws-evidence/`; the merge keeps it under `runs/`.
- **One review per branch.** `ws review` runs a mechanical precheck (stray logs, malformed SVGs, future dates, missing paths, deleted files still referenced), then a read-only reviewer against the 20-rule `checklist.md`; light-track branches review on a cheaper model.
- **A merge with a test gate.** `ws merge` merges only the reviewed SHA, refuses lines that add home paths, the username or configured names, runs the project's tests on the merged tree, undoes the merge on red, pushes on green, restores files the test run rewrote, and warns when the suite is slow.
- **Unattended chains.** `ws chain` runs a queue of steps (dispatch, wait, review, one automatic fix round, merge), waits out usage limits, carries review suggestions forward, and stops only on a failure, a gate or a judgment call.
- **Previews.** `ws serve` runs a project's preview command from a worktree or the main checkout under a memory cap.
- **Releases and sites.** `ws release` publishes a private repository's main branch (or its `RELEASE_PATHS`) as one audited commit per release on a public repository, with a clean-clone build attached to a GitHub release; `ws site` copies published files into a site project, checks them byte for byte, tests, pushes and waits until live.
- **An automation audit.** `ws audit` reads the run logs for work builders keep doing by hand.
- **Private overlays.** `config.local.sh`, `CLAUDE.local.md` and `lessons/<role>.local.md` hold an installation's own settings, preferences and lessons beside the shared files.
