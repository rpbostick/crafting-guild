# The orchestrator on OpenCode

Crafting Guild runs as an orchestrator under two clients: Claude Code reads `CLAUDE.md` and its SessionStart hook; OpenCode reads `AGENTS.md`, `opencode.json`, the cold-start plugin and `/cold-start`. Both drive the same `bin/ws` loop. This page records what the OpenCode documentation says, which mechanism replaces each Claude Code one, and how the two briefs are kept from drifting.

Sources were read on 2026-10-22. Every statement about OpenCode below names the page it comes from.

## What the pages say

### Rules and AGENTS.md

- OpenCode reads `AGENTS.md` from the project root for instructions local to that directory ([docs/rules](https://opencode.ai/docs/rules/)).
- A project `AGENTS.md` can be committed and shared with a team; a global `~/.config/opencode/AGENTS.md` holds personal rules ([docs/rules](https://opencode.ai/docs/rules/)).
- `AGENTS.md` wins over `CLAUDE.md`: when both are present in a directory, only `AGENTS.md` is used; `CLAUDE.md` is a fallback for projects without one ([docs/rules](https://opencode.ai/docs/rules/)).
- The `instructions` key in `opencode.json` adds more files, paths, glob patterns or remote URLs to the same context, and all of them are combined with `AGENTS.md` ([docs/rules](https://opencode.ai/docs/rules/), [docs/config](https://opencode.ai/docs/config/)).
- Remote instruction URLs are fetched with a five-second timeout ([docs/rules](https://opencode.ai/docs/rules/)).

### Config

- Project config is `opencode.json` in the project root, in JSON or JSONC, and it is safe to commit ([docs/config](https://opencode.ai/docs/config/)).
- Config sources are merged; a project config overrides global and remote configs only for the keys it sets ([docs/config](https://opencode.ai/docs/config/)).
- `OPENCODE_CONFIG` names a custom config file, loaded after the global config and before the project config ([docs/config](https://opencode.ai/docs/config/)).
- `.opencode/` holds project-level `agents/`, `commands/`, `plugins/`, `skills/`, `tools/` and `themes/` ([docs/config](https://opencode.ai/docs/config/)).
- The `instructions` key takes an array of paths and glob patterns to instruction files ([docs/config](https://opencode.ai/docs/config/)).
- The published config schema defines `share` with `"manual"`, `"auto"` and `"disabled"` ([schema](https://opencode.ai/config.json)). The config page describes config validation against that schema ([docs/config](https://opencode.ai/docs/config/)).

### Commands

- A markdown file in `.opencode/commands/` becomes a slash command named after the file; YAML frontmatter supplies `description`, `agent` and `model` ([docs/commands](https://opencode.ai/docs/commands/)).
- A command template can inject the output of a shell command with `` !`command` ``; commands run in the project root and their output becomes part of the prompt ([docs/commands](https://opencode.ai/docs/commands/)).
- `$ARGUMENTS`, positional `$1`, `$2`, and `@file` references are the other prompt substitutions ([docs/commands](https://opencode.ai/docs/commands/)).

### Tools

- OpenCode's built-in shell tool executes commands in the project environment; its permission key is `bash`, not the tool's name ([docs/tools](https://opencode.ai/docs/tools/)). `scripts/opencode_run.py` writes the shell rules under `bash` for that reason.
- The `question` tool asks the user during execution; each question has a header, text and a list of options, and the user can pick an option or type a custom answer; with several questions the user can move between them before submitting ([docs/tools](https://opencode.ai/docs/tools/)).
- The v2 copy of the tools page states that the shell tool has a two-minute default foreground timeout, that `timeout` is set in milliseconds when that is not suitable, and that `background: true` returns immediately and notifies the session when the call finishes; a background call has no timeout unless one is set ([v2/docs/tools](https://opencode.ai/v2/docs/tools)). The v1 tools page documents the shell tool without giving a timeout ([docs/tools](https://opencode.ai/docs/tools/)).
- The CLI page lists `OPENCODE_EXPERIMENTAL_BASH_DEFAULT_TIMEOUT_MS`, the default timeout for bash commands in milliseconds ([docs/cli](https://opencode.ai/docs/cli/)).
- The `question` tool's permission key is `question` ([docs/tools](https://opencode.ai/docs/tools/), [docs/permissions](https://opencode.ai/docs/permissions/)).

### Permissions

- Permission rules resolve to `allow`, `ask` or `deny` ([docs/permissions](https://opencode.ai/docs/permissions/)).
- Most permissions default to `allow`; `doom_loop` and `external_directory` default to `ask` ([docs/permissions](https://opencode.ai/docs/permissions/)).
- `external_directory` applies to any tool call that touches a path outside the working directory OpenCode was started in, including `read`, `edit`, `glob`, `grep` and many shell commands ([docs/permissions](https://opencode.ai/docs/permissions/)).
- Shell rules match the parsed command, so a pattern needs `*` to allow arguments (`"grep *"`, not `"grep"`) ([docs/permissions](https://opencode.ai/docs/permissions/)).

### Plugins

- Local plugins live in `.opencode/plugins/` or `~/.config/opencode/plugins/` and are JavaScript/TypeScript modules exporting hooks ([docs/plugins](https://opencode.ai/docs/plugins/)).
- The documented events include `session.created`, `session.idle`, `tool.execute.before`/`after` and `command.executed`; the plugins page's list has no "session start, inject prompt context" hook, and the examples use events for notifications and guards, not for adding the session's opening context ([docs/plugins](https://opencode.ai/docs/plugins/)).
- `@opencode-ai/plugin` 1.19.1's `dist/index.d.ts:265` declares an undocumented, experimental `experimental.chat.system.transform` hook, called with `{sessionID, model}` (the `sessionID` field is optional) and an appendable `output.system: string[]`; OpenCode 1.19.1 calls it for each model request and puts the appended text in the system prompt. The plugins page does not list it ([docs/plugins](https://opencode.ai/docs/plugins/)).

`.opencode/plugins/cold-start.js` closes the session-start gap. The hook runs `scripts/cold-start.sh --brief` once per session id, inheriting the session's environment so `WS_PROJECT` pinning still holds, caches the output and appends it to the system prompt behind a one-line header on every request; a failing or 20 s script appends a one-line note instead and the session continues. `/cold-start` remains the on-demand refresh mid-session. The same plugin implements `experimental.session.compacting` (`index.d.ts`: `{sessionID}`, an appendable `output.context: string[]`), so a compaction reads the context again and the session continues with the fresh text; a forced `POST /session/:id/summarize` on 1.19.1 re-read a brief file created after the first message, carried its new state into the summary, and the follow-up reply named the project. Because the hook is experimental and absent from the plugins page, an OpenCode upgrade has to re-check it. OpenCode discovers `.opencode/plugins` from the working directory, so reviews run `opencode run --pure` ("run without external plugins"). A builder cannot use `--pure`: the flag clears every plugin origin, including the run-events plugin its inline config names (the 1.19.1 binary's server plugin loader takes `plugin_origins` only when `OPENCODE_PURE` is unset). The builder names that plugin through `OPENCODE_CONFIG_CONTENT`, and the cold-start plugin returns early when `WS_RUN_EVENTS` is set, so a builder still never receives the brief.

## Choosing the reviewer

`ws review` picks the reviewer from the branch when neither `--agent` nor a non-empty `WS_REVIEW_AGENT` forces one: a branch whose every changed file is Markdown or under `docs/`, `plans/`, `reports/`, `lessons/`, `agents/` (or is `checklist.md`) reviews on OpenCode, and any other branch, or one with no changed files, reviews on Claude.

## The orchestrator's own config

`ws opencode-perms` writes the registered project paths and the shell rules to `~/.config/opencode/orchestrator.json`, not to the global `opencode.json`. Config sources are merged ([docs/config](https://opencode.ai/docs/config/)), so a rule in the global file also sits under the inline permissions a builder or review passes: its `bash` rules combine, and an `ask` left there waits on a prompt a headless run cannot answer, leaving it without a shell. The orchestrator loads the file as its custom config. The launcher does both in one command:

```
ws oc <slug>
```

It sets `WS_PROJECT` and `OPENCODE_CONFIG` and starts OpenCode in the workspace; it does not move `state/current`, so a second session stays on its own project. `ws oc <slug> --print` shows the underlying command.

`OPENCODE_CONFIG` is loaded after the global config and before the project config ([docs/config](https://opencode.ai/docs/config/)), so the orchestrator session still inherits the global providers, models and other keys. The builder and review launchers unset `OPENCODE_CONFIG`, so the orchestrator's rules reach only the orchestrator session; the global config is left to both. The command refuses to write a global `opencode.json` and prints the launch line after writing.

The memory directory is read-only for now: when `WS_MEMORY_DIR` is set, `ws opencode-perms` adds an `external_directory` allow and an `edit` deny for it, so the orchestrator reads memory and its edit tools cannot change it. Run the command again after changing the setting. The shell is not covered: `bash` allows any command outside the ask list, so a shell command could still write there. The `edit` deny has not been seen refusing an edit in a real session, so whether OpenCode matches it against an absolute path outside the working directory is still to be observed.

## Waking an idle session

An OpenCode session sits idle until something sends it a message, so a finished chain goes unnoticed. `ws wake <session> "<message>"` sends one, at once, `--at <time>` (anything `date -d` reads; a past time is refused), or `--when-chain-stops` (with the chain's last status added; refused when no chain runs). `ws wake list` shows what is pending, `ws wake cancel <id>` stops it.

`--every <OnCalendar>` repeats the message on a systemd calendar spec, validated first by `systemd-analyze calendar` (a bad spec is refused with that command's error and nothing is written). `--until YYYY-MM-DD` ends the repetition: the first fire after that date removes the job, its timer and its unit files, and logs the end in `wake.log` instead of sending the message. A recurring job keeps its files in `runs/<slug>/wake/` and a fire that fails still goes to `wake.failed`, while the timer stays for the next try.

`scripts/wake.sh` writes the job under `runs/<slug>/wake/` and, for a one-shot, starts a transient timer and service, `ws-wake-<slug>-<id>`, with `PATH` set, since the user manager's lacks `~/.local/bin`. A recurring wake instead writes `ws-wake-<slug>-<id>.timer` and `.service` under `WS_WAKE_UNIT_DIR` (default `~/.config/systemd/user`), with `OnCalendar=` and `Persistent=false` so a missed run is not replayed in a burst after a suspend, then reloads and enables them; transient units do not survive a reboot, unit files do. The service runs `opencode run --attach <url> --session <id> --format json -- <message>`. The session's client has to listen, and `ws oc <slug>` makes it: with no `--port` or `--hostname` of the caller's, it passes `--port <p> --hostname 127.0.0.1` for the first free port from `WS_OC_PORT` (4096) up and writes `<p>` to `runs/<slug>/oc.port` (a caller's `--port` is kept and recorded; `--print` shows the flag and writes nothing). The server is `--url`, else `WS_WAKE_URL` when set (empty by default), else `http://127.0.0.1:<runs/<slug>/oc.port>`, else `http://127.0.0.1:4096`. The session is an id, or `current`: the cold-start plugin writes the session's id to `runs/<slug>/session.id` on its first request, and `current` reads it, dying with "no recorded session id for <slug>; start the session with ws oc <slug>" when the file is missing. The orchestrator config (`scripts/opencode-perms.sh`) denies the `task` tool: a subagent session passes through the same `experimental.chat.system.transform` hook, so a child's id would overwrite `session.id` and `current` would wake the finished child; `ws ask` does that research job instead. So a session started with `ws oc` wakes with `ws wake current "<message>"` and `ws bg run <name> --wake current -- <command>`, no flags; `ws bg` resolves `current` when the command starts.

A server password comes from `OPENCODE_SERVER_PASSWORD` (and `OPENCODE_SERVER_USERNAME`) in the environment of `ws wake`. `systemd-run` gets the variable's name, so the value is on no command line and in no file under `runs/`; the transient unit holds it, readable by the same user through `systemctl --user show`. A recurring service instead names the variable in `PassEnvironment=`, after `systemctl --user import-environment` copies it from the scheduling shell into the user manager, so it is still in no unit file. A failed import stops the schedule with that command's error and writes nothing, rather than leaving a timer that would fail every fire. The imported copy lives only in the user manager's memory, not in the unit files, so it does not survive a reboot: a password-protected recurring wake has to be rescheduled after one. A message is on the service's command line, so it must not hold a secret.

The first JSON event from the session counts as delivered and goes in `runs/<slug>/wake.log`. With no event, the wake goes to `runs/<slug>/wake.failed` (time, id, session, server, reason, message on one tab-separated line): when `opencode run` exits without one, or after `WS_WAKE_TIMEOUT` seconds (900), when the client is killed. Cold start prints `WAKE FAILED` until `ws wake failed --clear`, and `ws wake failed` prints each one. A one-shot transient unit does not survive a reboot: a job whose units are gone prints `WAKE LOST` at cold start and in `ws wake list`, and `ws wake cancel <id>` removes it. `ws wake list` shows a recurring job's spec, its next run (from `systemctl --user list-timers`) and end date; `ws wake cancel <id>` disables its timer and deletes both unit files.

Tested with OpenCode 1.19.1, systemd 255, on a throwaway session of a local `opencode serve`: a message sent with `--attach --session` reached the idle session and the session remembered its earlier turns; the shell tool listed `command`, `timeout` and `workdir` and no `background`; a real `ws wake` delivered through a timer and the session quoted the message back; a real `--at` timer showed in `ws wake list` and `ws wake cancel` removed it; a real wake at a closed port landed in `wake.failed`; a real wake sent during a 25-second turn waited and joined that turn's next step, so a busy session takes it too. A closed port and an unknown session print the same `Session not found` and exit 1, so the reason names both readings. The password path, the `--when-chain-stops` path, cold start's lines and the `--every`/`--until` path (persistent unit files, the calendar check, list, cancel and expiry) are covered by stand-ins in `scripts/wake-check.sh`, not a real server or timer. A plain `opencode --port` TUI does listen on that port, and a real `ws wake` into its open session showed the message and the reply there with no keypress, seen in a tmux pane. `opencode run` wraps a message holding spaces in double quotes, so the session sees it quoted.

`ws bg run <name> --wake <session|current> -- <command...>` uses this same path when the command ends, so a long `ws wait`, `ws chain` or test run finishes without the session polling it: the session ends its turn, and the wake starts the next one with the exit code and log path. `ws bg` runs the command in its own session with `setsid`, records its pid, log and exit code under `runs/<slug>/bg/`, and `ws bg wait` returns that exit code; `ws bg stop` kills the process group. `--watch '<regex>'` (repeatable) starts a watcher per pattern that reads the command's log and reports the first matching line once, before the command exits, through the same wake path as "bg <name> matched '<regex>': <line>" (or appends it to `runs/<slug>/bg/<name>.matches` without `--wake`); `ws bg watch <name> '<regex>'` adds one to a running command, and `ws bg list` shows each pattern as pending or matched. A watcher reads the whole log, so a `ws bg watch` added after the line was written still fires. `scripts/bg-check.sh` tests it with stand-ins for `systemd-run` and `opencode`, so no model call is made.

## A browser for the session

An orchestrator on OpenCode has no browser of its own, so it loads previews through `@playwright/mcp` 0.0.84 (Apache-2.0), pinned exactly in `WS_BROWSER_MCP_VERSION`. `chrome-devtools-mcp` 1.12.0 (Apache-2.0) was the fallback and was not needed; `npm view` reports Apache-2.0 as the licence of both packages. `browser_mcp_json` in `scripts/lib.sh` is the one definition: `npx -y @playwright/mcp@<version> --headless --isolated --output-dir <XDG_RUNTIME_DIR-or-/tmp/ws-<uid>>/ws-playwright-mcp --allowed-origins "http://127.0.0.1:*;http://localhost:*"`, server name `playwright`, so its tools are `playwright_browser_navigate`, `playwright_browser_snapshot` and the rest. Without `--output-dir` the server writes `.playwright-mcp/` into the working directory, this repository. The folder is per user: a shared `/tmp` path let another user or session read and overwrite its page logs.

`ws opencode-perms` writes the entry to `~/.config/opencode/orchestrator.json`, the file only `ws oc` loads; run it once after this version arrives, then restart the session. The file is not rewritten by a later `WS_BROWSER_MCP_VERSION` bump, so `ws doctor` warns when it pins another version, with `ws opencode-perms` as the fix. Builders and reviews never see it: their launchers unset `OPENCODE_CONFIG`, their inline configs have no `mcp` key and deny unlisted tools, and the project `opencode.json` has none either. The selftest checks all of those beside the orchestrator's entry.

The origin list is Playwright's own, whose help says it is not a security boundary and does not affect redirects: it keeps a session on local pages, and a local page that redirects outward is not stopped by it. Browser binaries are Playwright's (`~/.cache/ms-playwright`), and a machine without a matching one needs `npx playwright install chromium`.

`ws doctor --parity` passes the same entry, with a private output folder, to its temporary server, serves a stand-in page on `127.0.0.1`, and has the model navigate there, take a snapshot, and try `https://example.com/`, in a session that allows only those two tools. The verdict reads the tool outputs: `worked` needs the page's one-run word in the snapshot and an `ERR_BLOCKED` on the public page. The server runs in its own process group; the probe stops the group on exit, then kills and names any child that survived.

Tested with OpenCode 1.19.1 on `opencode-go/deepseek-v4.1-flash`: a real `ws doctor --parity` printed `worked` with the page's word and the public page refused. The selftest covers the failure lines with a stand-in server.

## How the two briefs are kept from drifting

`docs/rules` says OpenCode uses `AGENTS.md` instead of `CLAUDE.md` when both exist ([docs/rules](https://opencode.ai/docs/rules/)). Loading `CLAUDE.md` through `instructions` as well would put two versions of the loop in context, and the Claude Code version's wait step would contradict the OpenCode one. So `AGENTS.md` is a complete brief, not an overlay.

The parts that are identical for both clients are not copied: `opencode.json` loads `CLAUDE.local.md`, `operator.local.md`, `lessons/orchestrator.md` and `lessons/orchestrator.local.md` by path ([docs/config](https://opencode.ai/docs/config/), [docs/rules](https://opencode.ai/docs/rules/)). One copy of those files serves both clients.

The part that can drift is the set of `bin/ws` commands named in the two briefs. `scripts/selftest.sh` extracts every `bin/ws <command>` from `CLAUDE.md` and fails when `AGENTS.md` does not name the same command. Adding a command to one brief and not the other is a red self-test.

## Delegation and the parity probe

Two commands keep a Claude-only capability reachable and tested from an OpenCode/DeepSeek session:

- `ws claude [--budget USD] [--schema file] [--dir path] [--allow <tool>] [--raw] <prompt-file|->` runs one Claude Code job in the current directory with `--output-format json`, `--max-budget-usd`, `--permission-prompts none`, read-only tools (`Read,Grep,Glob`) plus any `--allow`, and the optional `--json-schema`. It signs in checks first (`claude auth status`), never creates a worktree or a branch, prints the JSON result (or the reply text with `--raw`, cost on stderr), and exits 3 on a usage limit, 1 on a model error or a reply without a structured result. `WS_CLAUDE_BUDGET` (config.sh, defaults to `WS_REVIEW_BUDGET`) is the budget.
- `ws doctor --parity` runs one tiny structured-output job per agent (opt-in, paid). It reports whether Claude's `--json-schema` is enforced, on the `haiku` alias under a capped budget; a stop at that budget or a usage limit gets its own line, because neither says anything about structured output. For OpenCode it starts a temporary `opencode serve` on `127.0.0.1` with a random password, posts one prompt with `format: {"type":"json_schema","schema":…,"retryCount":2}`, and reports `enforced`, `failed: …` (including `StructuredOutputError`) or `unsupported: …` from the reply; the server is stopped in a trap and its session deleted. The server enforces the schema through a StructuredOutput tool, not the provider's JSON mode, and `opencode run` cannot request it. Those results are the decision point for moving builders to the server path. On the same server it asks for one `webfetch` of `https://example.com` and one `websearch`, each in a session that allows only that tool, and prints one line each: `worked: …`, `not available: …` (the server does not list the tool for the model, or the model made no call) or `failed: …`; every line but `worked` is a warning that builders keep the web relay (`ws web`). One more prompt opens a local stand-in page through the browser MCP (see [A browser for the session](#a-browser-for-the-session)). Then, with no model call, it writes a throwaway skill to a temp project's `.opencode/skills/`, reads `GET /skill?directory=<project>`, and prints one line: `loaded: …` when the throwaway is listed with its body and so is every skill under `~/.claude/skills`, `not loaded: …` naming what is missing, `not available: …` (a server with no skill list) or `failed: …`. Last, one paid Flash prompt creates a session in that project with only the `skill` tool allowed and asks the model to load the throwaway and reply with its marker: `worked: …` needs a completed `skill` call in the session and the marker in the reply, `not available: …` means the model made no call, and `failed: …` means the call or the reply failed. Builders deny the `skill` tool, so this concerns orchestrator sessions.

Tested with OpenCode 1.19.1: a real `ws doctor --parity` reported the throwaway and `two-orchestrators` as `loaded`, and then reported `opencode skill call: worked: called skill cg-parity-probe and replied with its marker`, so a model did call the `skill` tool. That run printed every parity line but the foreground call hit its timeout before the command exited, so no exit code was recorded; the skill-call verdict itself comes from the session's parts.

Tested with OpenCode 1.19.1: on `opencode-go/deepseek-v4.1-flash`, a real `ws doctor --parity` reported `worked` for both the fetch and the search. The selftest covers the other outcomes against a stand-in server. The tool call is in an earlier message than the prompt's reply, so the probe reads the whole session.

Tested with OpenCode 1.19.1: `scripts/selftest.sh` proves `ws claude`'s flags, schema refusal, raw output and limit exit with a stand-in; `ws doctor --parity` reports Claude's enforced schema and, against a stand-in HTTP server, OpenCode's `enforced` reply and its `StructuredOutputError`, and no server outlives either run; a real Claude 429 was reported as a usage limit, not a probe failure. `ws doctor` also checks the Claude sign-in and OpenCode's presence and credential, because reviews can need either client and delegation needs Claude.

Tested with OpenCode 1.19.1: a real `ws doctor --parity` on OpenCode 1.19.1 with `opencode-go/deepseek-v4.1-flash` reported `failed: StructuredOutputError: Model did not produce structured output (retries 0)`. The server's forced schema is not usable with this model, so builders stay on `opencode run` and `check-result` checks the branch; a non-thinking variant or another model has not been tried.

Tested with OpenCode 1.19.1: the selftest imports `scripts/opencode-plugins/run-events.js` with `node`, feeds stand-in permission, retry and 429 events, and checks `check-result`'s denial, recovered-retry and limit outcomes; the OpenCode stand-in dispatch shows the builder's inline config carrying the plugin.

## Not settled by the documentation

- The docs do not say what happens when an `instructions` path does not exist. Globs are accepted ([docs/config](https://opencode.ai/docs/config/)), which suggests a pattern that matches nothing is harmless, but that was not observed. `CLAUDE.local.md`, `operator.local.md` and `lessons/orchestrator.local.md` are private and excluded from a public release, so a public tree either ships those files or removes their entries from `opencode.json`.
- The v1 tools page documents the shell tool but gives no timeout ([docs/tools](https://opencode.ai/docs/tools/)); the two-minute figure comes from the v2 page ([v2/docs/tools](https://opencode.ai/v2/docs/tools)), which also states that a background call has no timeout unless one is set, and the CLI page confirms a configurable default exists ([docs/cli](https://opencode.ai/docs/cli/)). The installed OpenCode should be checked against the v1 page after an upgrade.
- `question`'s multi-select checkbox is not described on the v1 tools page; `AGENTS.md` therefore says to offer several applicable choices, and falls back to a numbered list when the tool cannot express that.
- OpenCode Go's quota response has not been captured. The 1.19.1 server recognises `GoUsageLimitError` in a provider response body, takes the wait from `retry-after`, and publishes a `SessionStatus` retry with `next` and `action.reason: "account_rate_limit"`; the run-events file will hold the real shape at the first limit. Until then `check-result`'s reset path is tested against those stand-in events, not a real 429.
