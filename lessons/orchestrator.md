## Working with Patrick
- Present decisions with the AskUserQuestion prompt: recommended option first and labelled, at most four per call, in rounds. He usually answers "all recommended". Read a free-text answer literally ("show me both on different ports", "a, then come back to c later").
- Ask before any infrastructure change (replacing a layer, adding a service, changing how builders are launched). He wants to be in the loop.
- Every date and time you write comes from `TZ=$WS_TZ date` run in the same step. After 18:00 local, the UTC date is already tomorrow.
- He checks visual changes himself on a preview server before the merge. Previews on :8801 and up, the live app on :8800, builders' own browser checks on 8790 to 8799. Pages made for him to look at (comparisons, review pages) are served the same way from the scratchpad (`python3 -m http.server 88xx --directory …`), not published as claude.ai artifacts (2026-10-01); a tool he uses from several computers with saved state is the exception (private artifact with `db`). Every preview: ask with AskUserQuestion whether to open it in his browser, and on yes run `firefox --new-tab <url>` (Patrick, 2026-10-01).
- Before a merge that changes how a database is written, copy the database aside first.
- A test-count claim cites the log it came from.

- Nothing goes public without `release-audit.md` passing and Patrick seeing the findings. colorwright's static build shipped dated comments quoting him to the public site (2026-09-28).
- Automate what repeats (Patrick, 2026-10-01): when a builder or I would do something a second time, it becomes a test, a committed script the suite runs, or a `ws` command. Run `ws audit` when cold-start says it is due and turn its top finding into the next tool fix or light task. Sequential steps go in a queue for `ws chain`, not hand-driven.

## Running builders
- Parallel builders share the CPU, not only the plan. Spikes and light builds run side by side fine; a render-heavy builder alongside a merge made the merge's suite two to three times slower (colorwright, 2026-09-26). The usage limit stopped no run in 42 hours. Merge when nothing heavy is running, and every dispatch gets a budget.
- A missing grant stalls a builder silently. Name every command the task needs and pass extras with `--allow`. Tell the task to use one command per Bash call.
- A builder cannot copy a file in from another repo: `cp` from outside its worktree is denied even with `--allow "Bash(cp *)"` (site-fw rounds 2 and 3, 2026-09-28). Copy cross-repo assets into the worktree yourself before dispatch, or after it finishes. Flags go before the builder name; dispatch refuses them after it.
- When a run stops on the usage limit, `ws chain` waits for the reset and resumes it (2.2.4). Outside a chain, re-dispatch after the reset with a task that says to resume.
- Do not edit files an open branch also touches. Put the edit in that branch's task.
- Never `cd` in a Bash call. It moves this session's working directory.
- Two sessions, two projects: `state/current` is one file, so the second `ws <slug>` moves it under the first. Sessions are pinned by `WS_PROJECT` since 2.1.2, but a session started any other way is not; when cold-start prints `CONFLICT` or `not pinned`, use `--project` on every command (found 2026-09-27 testing 2.1.0 from a terminal).
- Review once per branch, before merge. A fix round is for a real defect or something he would see; suggestions carry forward in the next task on that code.
- `ws merge` needs the project's main checkout free of modified tracked files; untracked files are fine. v1's hooks used to append to `reviews/checklist-proposals.md` behind your back; check `git status -uno` first.
- `ws merge` refuses any verdict but `merge`. When Patrick overrides a fix-first review, pass `--no-review` (the SHA pin and the test gate still apply) and record his decision in the plan.
- The machine has 14 GB and no swap. A spike's probe script reached 7.6 GB and the OOM kill took down VS Code with the orchestrator and both builders (fw-bodyshape, 2026-09-27). Builders are capped at `WS_BUILDER_MEM` since 2.1.3; tell image-processing spikes to hold one raster at a time.
- A builder that backgrounds a long script loses it when the run ends (cw-heads-spike part 2, 2026-09-26). Tell spikes with long render jobs to run them in the foreground, split if needed.
- **Two orchestrators at once (open investigation, 2026-09-28).** When a session closed at 16:42, Claude Code's daemon forked it into a background session (`claude daemon run --origin transient` → `--fork-session --resume <old id>`); the new `ws bike-weather` window started 4 s later. For 16 hours both acted on figurewright: two reviews of fw-dress, a fix round dispatched by the background one. Patrick had one window open. Until explained: on resume, run ListAgents and `ps -eo pid,args | grep fork-session`; a peer orchestrator on this workspace means stop and tell Patrick. Seen again 2026-10-01 ~16:10 MDT (CLI 2.1.286): after Patrick closed a `ws figurewright` session, the daemon resumed it as `bg-pty-host … --fork-session --resume`, woken by a background-task notification (a `ws wait` finishing); the fork stood down. To find out: what makes the CLI background a closing session (a setting, a running `ws wait`, auto mode?), and whether cold-start should detect a peer.
- Not a peer: VS Code's Claude extension resumes its last panel conversation when VS Code opens (`native-binary/claude … --resume=<id>`, parent `code`, cwd `~`). It idles at $0 unless typed into. Only a `--fork-session` process or one whose cwd is this workspace counts (2026-09-29).
- Closing the session kills its background `ws wait`, not the builder (it runs in its own systemd scope): after a resume, read `runs/<slug>/<name>.result.txt` or wait again (2026-09-28). A resumed session gets a new scratchpad, so rebuild any review page there.
- Bash reads a running script from disk as it goes: editing `scripts/chain.sh` (or any script) in place while a chain runs can make it execute shifted text. Write the new version to a temp file and `mv` it over (2026-10-01).
- Never `pgrep -f`/`pkill -f` a pattern that appears in your own Bash command: it matches the shell running it (a wait loop spun for 10 minutes; a `pkill` killed its own call, 2026-09-29). Run parallel jobs with `&` and `wait`, and kill by PID.
- `ws merge` can take over 10 minutes when builders run alongside; run it with `run_in_background`.
- A background `ws wait` is killed at the Bash tool's default 30-minute background limit; pass `timeout` up to 7200000 for long runs (2026-10-02, a 180m round's wait died at 30 min).
- Mark small, low-risk tasks `Track: light` (code + unit tests, no evidence ceremony; the merge gate runs the suite). Evidence formatting doesn't block reviews; `ws merge` refuses a branch that adds home paths or the username, so scrub them on the branch first. (Patrick, 2026-09-26: a two-outfit colour split took an hour of process.)
- The timeout follows the track: 45m for `Track: light`, 120m otherwise (`config.sh`); pass `--timeout` (minutes, or `2h`; before 2.2.8 a bare number was seconds) for a bigger build and `ws wait <name> <minutes>` to match. A timed-out run can die without writing its result (cw-p20-2b, 2026-09-27): check `git log` and `git status` in the worktree, then resume.
- Builders run only the tests for what they touched (v2.1.0); the merge gate runs the suite. `ws merge` prints the suite's time and warns over `WS_SUITE_WARN_S`; when it warns, a light task to speed up the slowest test files is the next thing to dispatch.
- Reuse before building (Patrick, 2026-10-01): research existing open-source programs and libraries before any build, more research the bigger the build: minutes for a small change, a research spike before a new tool or a substantial module. Every build task carries a `## Prior art` section; `ws dispatch` warns when it is missing. (The synthesis review page was dispatched with a hand-written diff while jsdiff exists.)
- Check a provider's real behaviour before writing a fix task about it: a task premise ("Open-Meteo times shift at DST") that was never verified cost a fix round (skywright sky-ride, 2026-09-27). A live or historical API call takes a minute.
- Repos state reasons, never who or when; plans keep attribution. Builders copied task wording ("Patrick, 2026-09-29", "the operator: …") into ~800 comment lines across colorwright and figurewright, scrubbed 2026-09-29. Write task requirements plainly; dispatch and merge now refuse attribution (`WS_ATTRIBUTION_RE`).
