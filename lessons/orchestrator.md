# Lessons: orchestrator

Always loaded. Keep under 40 lines: add a line when something costs real time, delete a line when it stops being true. Lessons that name your own projects, people or dates go in `lessons/orchestrator.local.md`, read after this file.

## Working with the operator
- Present decisions as a question with options, the recommended option first and labelled, a few per question, in rounds. Read a free-text answer literally ("show me both on different ports", "a, then come back to c later").
- Ask before any infrastructure change (replacing a layer, adding a service, changing how builders are launched).
- Every date and time you write comes from `date` run in the same step (`TZ=$WS_TZ date` only when `config.sh` sets `WS_TZ`). West of UTC, the UTC date is already tomorrow in the evening (from 18:00 at UTC−6).
- Visual changes are checked on a preview server before the merge (`ws serve`, from `WS_PREVIEW_PORT` up). A gate page opens with the whole subject (every variant, main beside the branch) before any close-up: steps judged on 3× close-ups pass while the whole reads wrong. Then what to look at in a sentence, the numbers, at most four pictures per point, a question under each; the builder's full page is a link. A page of 168 images answers nothing.
- Before a merge that changes how a database is written, copy the database aside first.
- A test-count claim cites the log it came from.
- Nothing goes public without `release-audit.md` passing and the operator seeing the findings: a static build can ship dated comments quoting people to a public site.

## Running builders
- Parallel builders share the CPU, not only the plan. Spikes and light builds run side by side fine; a render-heavy builder alongside a merge makes the merge's suite two to three times slower. The usage limit kills every running builder at once, sometimes with the wrapper that writes the result (`ws wait` writes it then); their work stays in the worktrees: `ws chain` waits for the reset and resumes the run; outside a chain, re-dispatch after the reset with a task that says to resume. Merge when nothing heavy is running, and every dispatch gets a budget. Builders run a whole jest suite with `--runInBand`: parallel jest workers are killed at the builder memory cap.
- A missing grant stalls a builder silently. Name every command the task needs in its `## Commands` section (dispatch grants each by its first words) and pass extras with `--allow`, spelled as the task spells them: `npm install *` does not cover `npx expo install`. Tell the task to use one command per Bash call. Builders have `git restore`, `git clean -f -- <path>`, `git ls-tree`, `stat`, `sha256sum` and `file`; plain `rm` and `mv` are denied. `cp` from outside the worktree is denied even with `--allow "Bash(cp *)"`: copy cross-repo assets in yourself before dispatch. Flags go before the builder name.
- A builder that needs a web source returns `partial` with `web_requests`, and `ws chain` stops on "web requests": read them with `ws web <name>`, answer a search with a URL (`approve <n> --url <url>`), approve or deny each, then `ws web <name> resume` (budget and timeout flags as for dispatch). Do not fetch by hand into a worktree.
- `ws merge` needs the project's main checkout free of modified tracked files; untracked files are fine. Check `git status -uno` first. It can take over 10 minutes when builders run alongside: run it with `run_in_background`.
- `ws merge` refuses any verdict but `merge`. When the operator overrides a fix-first review, pass `--no-review` (the SHA pin and the test gate still apply) and record the decision in the plan.
- Builders are capped at `WS_BUILDER_MEM` and previews at `WS_SERVE_MEM`: on a 14 GB machine without swap, one probe script reached 7.6 GB and the OOM kill took the editor, the orchestrator and both builders with it. Tell image-processing spikes to hold one raster at a time. `expo start` starts a Metro worker per core (~700 MB each): Expo `PREVIEW_CMD`s pass `--max-workers 2`.
- After a hard machine crash (no shutdown in `journalctl -b -1`), run `git fsck` in the project before anything else: a commit cut off mid-write leaves empty object files that break its branch. Delete the empty files, point the branch back at its base with `git update-ref`, `git reset` the worktree (files stay) and recommit. An Edit cut off mid-write leaves a complete `<file>.tmp.<pid>.<hex>` beside the old file. Restart builders one at a time; the chain stops on a worktree with no run until a resume task is dispatched by hand.
- Two lanes whose code doesn't overlap still share the README, `package.json`, the app shell and the stylesheet: every UI feature adds a line to each. Plan the second lane's merge as a `git merge main` step for its builder, or keep UI tasks in one lane and run harness or core tasks beside it.
- Gate a change only on a judgement the operator alone can make (how it looks, how it feels to play), and say in plain words what the feature is for and what to judge. Developer tooling that tests prove merges on the evidence; asking the operator to re-run the builder's tests adds nothing.
- A builder that backgrounds a long script loses it when the run ends. Tell spikes with long render jobs to run them in the foreground, split if needed.
- Claude Code can resume a closed session in the background (`--fork-session --resume <id>`), woken by a background-task notification such as a `ws wait` finishing; two orchestrators then act on one project. On resume, run `ps -eo pid,args | grep fork-session`: a peer orchestrator on this workspace means stop and tell the operator. An editor extension resuming its last conversation (`--resume=<id>`, cwd elsewhere) is not a peer.
- Closing or crashing the session kills its background `ws wait`, not the builder (its own systemd scope): after a resume, read `runs/<slug>/<name>.result.txt` or wait again. A chain whose log ends in `Terminated` with no `runs/<slug>/chain.pid` died with it too: re-run `ws --project <slug> chain <queue>`; it skips merged steps and waits on the run in progress. `ws chain-wait` only waits on a live chain. A resumed session gets a new scratchpad, so rebuild any review page there.
- Bash reads a running script from disk as it goes: editing `scripts/chain.sh` (or any script) in place while a chain runs can make it execute shifted text. Write the new version to a temp file and `mv` it over.
- Never `pgrep -f`/`pkill -f` a pattern that appears in your own Bash command: it matches the shell running it (a wait loop spins forever; a `pkill` kills its own call). Run parallel jobs with `&` and `wait`, and kill by PID.
- Mark small, low-risk tasks `Track: light` (code + unit tests, no evidence ceremony; the merge gate runs the suite): full process on a small change can take an hour. Evidence formatting doesn't block reviews; `ws merge` refuses a branch that adds home paths or the username, so scrub them on the branch first.
- The timeout follows the track: 45m for `Track: light`, 120m otherwise (`config.sh`); pass `--timeout` (minutes, or `2h`) for a bigger build and `ws wait <name> <minutes>` to match. A timed-out run can die without writing its result: check `git log` and `git status` in the worktree, then resume.
- Reuse before building: research existing open-source programs and libraries before any build, more research the bigger the build: minutes for a small change, a research spike before a new tool or a substantial module. Every build task carries a `## Prior art` section; `ws dispatch` warns when it is missing. A hand-written diff where jsdiff exists is the failure this prevents.
- When the operator reports that a control doesn't work in a game or app built on someone else's content, ask which screen first and reproduce that exact screen before reading code: the original may ignore that input there (a game's name-entry screen ignoring Start).
- Check a premise before writing a task on it, including a reviewer's suggestion ("this API's times shift at DST", "feature-detect with `'oncancel' in input`" when every element has it): each wrong premise costs a fix round; an API call or one web search takes a minute.
- Repos state reasons, never who or when; plans keep attribution. Builders copy task wording ("<name>, <date>", "the operator: …") into comments, hundreds of lines across a project. Write task requirements plainly; set your names in `WS_ATTRIBUTION_RE` (config.local.sh) so dispatch and merge refuse them.
- `ws chain` skips a queue step whose name was merged after its task file was first committed. Check `git log --merges | grep agent/<name>` before reusing a short name with an old task file.
- Before a task states which frame, joint set or registration to use, have the builder measure the candidates first: a choice made from reasoning can cost two runs before the measured option wins.
- A project that depends on a sibling by `file:../<name>`: once a builder runs `npm install` or `npx expo install`, its worktree gets its own node_modules and the relative link points into `.worktrees/`. Dispatch links each such sibling into `.worktrees/`; jest and tsc pass without it, which hides the break.
- A builder worktree whose `node_modules` is a symlink to the main checkout shares Metro's transform cache with every other worktree: a preview of a second worktree can serve another worktree's cached entry. Expo `PREVIEW_CMD`s pass `--clear`; a builder's `expo export` in such a worktree is exposed the same way.
- Switch course on the second partial run of one task name, or the third feel-tuning round of one page: change the task (the operator's one-sentence fault as its done-when verbatim, measure first, a slider page to tune live), not the budget. One task ran 8 times over 4 days ($84) after its rule was stated on day one.
- `runs/*/merge.lock` files always exist: a merge holds one with `flock` while its tests run. A script that waits for merges tests `flock -n <lock> true`, never the file's existence, or it waits forever.
